問候冒險者 — 第一版數值與公式帳本

哪邊是「程式固定的公式」、哪邊是「我設計的數值（待你討論）」。更新於 F3 Resolver 層施工期。

一句話：公式（formula）＝ kernel，是程式裡固定的數學形狀，本身不含任何可調數字； 數值（params）＝我為每個 resolver 設計並寫進內容的係數／機率／門檻。換一份 Content Pack 只換數值，公式不動。

所以「哪邊有公式」＝下面〈公式清單〉；「哪邊有我設計的數值」＝〈我設計的數值〉每一張卡片。 每一項都標了落點（哪個檔案）與狀態。標 待實作 的數字是我的提案， 尚未寫進程式，正是要給你先看、可改的部分。

已實作 已進 code／content，測試綠 待實作 公式已定、數值是我的第一版提案，尚未落地 需你拍板 牽涉新資料概念或 schema 變更，動手前想先跟你確認

1. 公式清單（程式側，固定形狀，零魔數）

這些是 src/data-runtime/kernels.ts 裡的 kernel。它們只吃 params＋inputs 回傳數字， 程式碼裡沒有任何可調數值（規範 §7.1）。每個 resolver 挑一個 kernel 當公式，再由內容餵它 params。

公式（kernel）算什麼典型用途
weightedLinearProductbias + Σ wᵢ·inputᵢ（或乘積式）＋夾限傷害、治療、物價微調
logisticCurve / logisticRollp = 1/(1+e^−(bias+Σ wᵢ·inputᵢ))，可夾 floor/ceil；roll 版用 RNG 擲成敗招募成功、留隊、各種成功率
monotonicAdjustclamp(base + up·↑ − down·↓, min, max)好感變化、脫隊傾向
thresholdTable分段查表：input ≤ 門檻 → 取值依距離定期限、依等級定品級
piecewiseLookup分段線性內插非線性曲線（產量、縮放）

3. 我設計的：數值（第一版方案，待討論）

以下每張卡：公式＝用哪個 kernel；我設計的數值＝我提的第一版 params；落點＝數值會寫進哪。 標 待實作 的數字都還沒進程式，改起來零成本。

戰鬥傷害 combat-damage已實作

公式：weightedLinearProduct（linear）。輸入：行動者主屬、目標主屬（依傷害管道選屬性）。

damage = clamp( bias + w_atk·行動者屬 − w_def·目標屬 , min=1 )

我設計的數值（已落地）：bias = 5、w_atk = 1.5、w_def = 1.0、clampMin = 1（三通道共用）。

管道→屬性（我定的對應）：physical→muscle、magic→intelligence、instrument→charisma。

數值：content-source/core/combat-resolver-params.ts（3 筆 weighted-product-params）； 公式接線：src/app/content/combat-power-resolvers.ts（shape combat:weighted-power）。 resolver 測試綠（20 攻 vs 10 防 → 傷害 25）。未改 schema。 備註：combat context 尚未接進 ContextAssembler，所以還沒能在「一整場戰鬥」裡跑——那是下一個接線增量。

戰鬥治療 combat-heal已實作

公式：weightedLinearProduct（linear）。輸入：行動者 intelligence。

heal = clamp( bias + w·行動者intelligence , min=1 )

我設計的數值（已落地）：standard = bias 5 / w 1.2；potent = bias 10 / w 1.6；clampMin = 1。

戰鬥 CTB 調整 combat-ctb-adjustment已實作

公式：weightedLinearProduct（linear，常數項）。輸入：無（固定延遲量）。

ctbDelta = bias

我設計的數值（已落地）：light = 10、standard = 20、heavy = 35（延後目標的 CTB 點數）。 控制抗性折算已在 combat 主路處理。

招募成功 recruitment-success待實作

公式：logisticRoll。輸入：玩家隊目前正式人數、招募者魅力/加成。

p = logistic( bias + w_cha·招募者charisma − w_size·目前人數 ) , floor 0.05 , ceil 0.95

我設計的數值（提案）：bias = −0.5、w_cha = 0.04、w_size = 0.25、floor = 0.05、ceil = 0.95。

人越多越難招（w_size 減項）；落點：logistic-roll-params 定義。

成員離隊 member-departure待實作

公式：logisticRoll。輸入：工作淨收益缺口 workNet、隊長抵抗 leaderResistance。

p = logistic( bias + w_gap·缺口 − w_res·隊長抵抗 ) , floor 0.00 , ceil 0.50

我設計的數值（提案）：bias = −2.5、w_gap = 0.02、w_res = 0.03、floor = 0、ceil = 0.5。

預設偏低（bias 很負）：新局幾乎不會有人離隊；缺口大才升高。

射程與距離（定案；schema 已加）已定案

射程＝格數（非分類）：武器 reachCells（近戰1／雙手・長柄2／射擊4-6／施法1）＋招式 extraReachCells（多數0，魔法/治療 +6）。有效射程 = 武器/怪物格數 + 招式額外。

距離 = 攻方離前排 + 守方離前排 + 1（不管左右）　→　合法目標：距離 ≤ 有效射程

前對前=1、雙方後排=5、後打敵前=3。combatDistance 已實作（純結構函式）；schema 三欄已加。 「近/中/遠」招式分類收斂掉（射程來自武器，不是招式類別）。落點：contracts + combat/state.ts。 下一步：武器/招式 reach 內容值 → handler 算有效射程傳入 target resolver 做距離過濾。

命中／迴避／格擋（沿用副屬性 + BM 公式，非發明）待實作

命中是副屬對抗，不是憑空基礎值。命中/迴避/格擋副屬由 statistics 服務算出「分數」。

命中率 = clamp(15,95, 70 + (命中分數 − 迴避分數) × 0.25) 格擋率 = clamp(0,75, 格擋分數 × 0.25)（守勢允許時）；格擋吸收 raw/(raw+80)；減傷 raw/(raw+120)

公式本體照既有平衡模型，不發明。目前戰鬥 dealDamage 必中——要新增命中/格擋 roll（miss 不套傷害、 成功格擋吃吸收）。需接 statistics 副屬查詢。這是最重一塊。

距離修正：傷害／命中／CD（我設計的數值，待討論）待實作

距離 3 = 標準；越近越有利、越遠越不利。遠距代價主要是命中變差（打不準），非狂砍傷害。 命中補正以 raw 加減加在攻方命中分數上（與狀態同機制），補正後才進命中率公式。
